01 — Project Summary

สรุปโปรเจกต์

เราดูแลหลายเกมแต่จับดราม่าด้วยตาคน — ช้าและพลาดได้ Crisis Radar เปลี่ยนให้ AI เฝ้าคอมเมนต์ทุกเพจตลอดเวลา แล้วเตือนทีมตั้งแต่คอมเมนต์ลบเริ่มพุ่ง ไม่ใช่ตอนไฟลามแล้ว

ปัญหา

บริษัทเราเป็น agency ดูแลหลายเกม (Talesrunner, WarzTH, TOSM, CabalX, Cabal Mobile ฯลฯ) ชุมชนหลักอยู่บน Facebook ทุกวันนี้ทีม Community ต้องนั่งไล่ส่องคอมเมนต์หลายเพจด้วยตาเอง เพื่อจับว่ามีดราม่า บั๊ก หรือคำร้องเรียนโผล่ไหม

ผลคือช้า พลาดได้ และมักรู้ตัวหลังเรื่องลุกลามไปแล้ว ซึ่งกระทบภาพลักษณ์แบรนด์ของลูกค้าโดยตรง

สิ่งที่ทำ

เครื่องมือที่ทำงานเป็น workflow ต่อเนื่อง 4 ขั้น: ดึงคอมเมนต์ → จัด sentiment และ topic ด้วย AI → ตรวจจับการพุ่งผิดปกติของคอมเมนต์ลบ (spike) → แจ้งเตือนทีมทันที พร้อม dashboard สรุปสถานะรายแบรนด์

จุดต่างจาก sentiment dashboard ทั่วไป

แกนของ Crisis Radar คือ early-warning ไม่ได้แค่ป้ายว่าคอมเมนต์ไหนบวกหรือลบ แต่ตอบว่า “ตอนนี้กำลังมีวิกฤตไหม เรื่องอะไร รุนแรงแค่ไหน”

และถ่วงน้ำหนักด้วย reach ด้วย — คอมเมนต์ลบที่คนแห่ไป like หรือ reply เยอะ ย่อมอันตรายกว่าคอมเมนต์ลบที่ไม่มีใครเห็น

ขอบเขตเดโม่ (Phase 1)

  • 1 แบรนด์: Talesrunner · 1 ช่องทาง: Facebook
  • Pipeline ครบวงจรทำงานได้จริงบน synthetic fixture และผ่าน test ทั้งหมด (ดูหัวข้อ 04)
  • ออกแบบ connector ให้ สลับไปใช้ Facebook API จริงได้ทันที เมื่อได้สิทธิ์ page admin

คุณค่าเชิงธุรกิจ — ทำไมคุ้มลงทุน

T1–T2b · ความแม่นของ AI และคุณค่าของชั้น LLM

เทียบคำตอบที่ควรเป็น (gold) กับที่ hybrid ตอบ: positive 6/6 ถูก · negative 13/13 ถูก · neutral 4/5 ถูก (เคสที่พลาดเป็นคอมเมนต์ก้ำกึ่งที่เอนไปทางลบ)

จุดขายของ hybrid — เคสประชดที่ lexicon อ่านไม่ออก

“ดีจริง ๆ นะคะที่ล่มตอนคนกำลังจะเล่น ขอบคุณมากค่า”

lexicon เห็นแต่คำว่า “ดี” และ “ขอบคุณ” จึงอ่านเป็นกลางหรือบวก แต่ชั้น LLM เห็นบริบทคำว่า “ล่ม” บวกน้ำเสียงประชด จึงแก้เป็น ลบ ได้ถูกต้อง

ต้นทุนคุมได้: เดโม่ส่งต่อให้ LLM แค่ 8 จาก 34 เคส (24%) เฉพาะที่ lexicon ไม่มั่นใจเท่านั้น

ข้อจำกัดที่ขอระบุตรง ๆ

labeled set นี้เป็น curated set ขนาดเล็ก (24 เคส) — เป็น smoke test เพื่อพิสูจน์ว่า logic ทำงานถูก ไม่ใช่ benchmark ที่บอกได้ว่าจะ generalize

ตอนขึ้น production ต้องมี labeled holdout ชุดใหญ่จากคอมเมนต์จริงมาวัดซ้ำ

Branch strategy

ใช้แบบเดียวกับที่ทีมใช้กับโปรเจกต์อื่น

  • main — เวอร์ชันเสถียร / เดโม่
  • dev — พัฒนา feature (ต่อ API จริง, เพิ่มช่องทาง)

คำสั่งรัน

git clone <repo-url> && cd crisis_radar

python3 run_demo.py           # เดโม่ใช้ stdlib ล้วน ไม่ต้องติดตั้งอะไรเพิ่ม
python3 tests/run_tests.py    # รัน test ทั้ง 9 เคส offline
สถานะ Repo URL

ยังไม่ได้ push — ตรวจสอบแล้วว่า repo ปัจจุบันมี branch main ในเครื่องแต่ยังไม่ได้ตั้ง remote จะ push เมื่อยืนยันปลายทาง (GitHub ส่วนตัวหรือขององค์กร) แล้ว

07 — Security

ความปลอดภัยและความเป็นส่วนตัว

Crisis Radar สนใจ สัญญาณรวม ว่ามีดราม่าไหม เรื่องอะไร รุนแรงแค่ไหน — ไม่ได้สนใจตัวบุคคล จึงออกแบบให้ไม่ต้องเก็บหรือเปิดเผยตัวตนผู้คอมเมนต์ตั้งแต่แรก

1 · PII — ข้อมูลส่วนบุคคล

มาตรการทำอะไรโค้ด
Mask ชื่อชื่อผู้คอมเมนต์ถูก hash เป็น user_xxxxxx ตั้งแต่ตอนโหลด — ก่อนเก็บและก่อนเข้า AIsecurity.mask_author
Scrub ในข้อความแทนเบอร์โทรหรืออีเมลที่คนอาจแปะไว้ในคอมเมนต์ด้วย [phone] / [email]security.scrub_pii_in_text
ตามตัวกลับไม่ได้ใช้ salt + sha256 — ยังนับ unique user ได้ แต่ย้อนกลับไปหาว่าเป็นใครไม่ได้ตรวจใน Test T5

พิสูจน์แล้วใน Test T5 — output ทุกไฟล์ (classified.json, dashboard.html) ไม่มีชื่อจริงหลุด

2 · ความลับและ Credentials

  • ไม่ commit token หรือคีย์ลง git — อ่านจาก env var ทั้งหมด (ANTHROPIC_API_KEY, FB page token)
  • salt ของ hash ย้ายไป env var ตอน production
  • .gitignore กัน .env, ไฟล์ generated และ cache

3 · การดึงข้อมูล (Scraping / API)

  • เดโม่ pipeline: ใช้ synthetic fixture — ไม่แตะข้อมูลจริง ไม่มีความเสี่ยงกฎหมาย
  • ดึงจริงช่วง prototype: Apify (แนะนำ) หรือ Playwright + session ของผู้ใช้เอง โดย mask PII ทันทีที่เข้า pipeline
  • Production — ทางที่ถูกต้อง: ใช้ Meta Graph API + Page access token ของเพจที่บริษัทเป็นแอดมิน ถูก ToS เสถียร และไม่ต้อง scrape
  • ระหว่าง prototype ถ้าจำเป็นต้อง scrape: rate-limit อย่างสุภาพ เคารพ robots เก็บเฉพาะที่จำเป็น และใช้ภายในองค์กรเท่านั้น

3.1 · PDPA

แหล่งความเสี่ยง PDPAการรับมือ
เพจ publicต่ำ คอนเทนต์สาธารณะmask PII + ใช้ภายในองค์กร
กลุ่ม (private)สูง สมาชิกคาดหวังความเป็นส่วนตัวเริ่มทีหลัง ต้องมีฐานทางกฎหมาย (legitimate interest) และเก็บเชิงรวม (aggregate) ไม่ระบุตัวบุคคล

เดโม่ Phase 1 จึงเริ่มจาก เพจ public ก่อน แล้วค่อยพิจารณากลุ่มเมื่อเคลียร์ประเด็นกฎหมายแล้ว

4 · Data Governance

  • เก็บเท่าที่ใช้: ข้อความคอมเมนต์ (scrub แล้ว) + เวลา + reach + topic/sentiment
  • ไม่เก็บ: โปรไฟล์ผู้ใช้ รูป เพื่อน หรือข้อมูลการเงิน
  • Dashboard เข้าถึงได้ภายในทีมเท่านั้น — ตอน deploy จริงจะใส่ auth

5 · ความเสี่ยงที่รู้ตัวและการรับมือ

ความเสี่ยงการรับมือ
AI จัด sentiment ผิด (ประชด / สแลง)hybrid + human-in-the-loop ก่อนออกแถลง — ไม่ให้ AI ตัดสินคนเดียว
False alarmTest T4 คุม threshold และปรับต่อเนื่องช่วง pilot
