# 2. Before – After Workflow

## Before (วิธีทำงานปัจจุบัน)
ทีม Community เฝ้าภาพลักษณ์แบรนด์ด้วยการ **ไล่ส่องด้วยตา (manual monitoring)**

| ขั้น | ทำอะไร | ปัญหา |
|---|---|---|
| 1 | เปิด Facebook ทีละเพจ (หลายเกม) วนดูคอมเมนต์ | กินเวลา, ต้องทำหลายรอบ/วัน |
| 2 | อ่านเอง ตีความเองว่าคอมเมนต์ไหนบวก/ลบ/ร้องเรียน | อัตวิสัย, คนละมาตรฐาน |
| 3 | รู้สึกเอาเองว่า "วันนี้ดราม่าเยอะ" | ไม่มีตัวเลข baseline เทียบ, พลาดช่วงนอกเวลางาน |
| 4 | พอเห็นว่าเริ่มลุกลามค่อยรายงานหัวหน้า | **มักช้า** — ไฟลามไปแล้ว |

**จุดเจ็บ:** lead time ในการ "รู้ตัว" ช้าและไม่แน่นอน ขึ้นกับว่าใครเวรเฝ้าและตาถึงแค่ไหน

## After (ด้วย Crisis Radar)
AI ฝังอยู่ใน workflow เตือนภัยอัตโนมัติ คนโฟกัสที่ "การตัดสินใจ/ตอบสนอง" แทน "การเฝ้า"

| ขั้น | ทำอะไร | ใครทำ |
|---|---|---|
| 1 | ดึงคอมเมนต์ทุกเพจอัตโนมัติตามรอบ | ระบบ (connector) |
| 2 | จัด sentiment + topic ด้วย AI (ประชด/สแลงไทยผ่านชั้น LLM) | ระบบ (hybrid classifier) |
| 3 | เทียบ baseline → ตรวจ spike + ถ่วง reach → ให้สถานะ NORMAL/WATCH/CRISIS | ระบบ (crisis detector) |
| 4 | **เด้ง alert เข้า Discord** พร้อมสรุปประเด็นร้อน + คอมเมนต์ไวรัล + **ทีมที่ต้องรับเรื่อง** | ระบบ → คน |
| 5 | ทีมเข้าไปตอบ/ออกแถลง โดยรู้ทันทีว่าเรื่องอะไร รุนแรงแค่ไหน | คน (ตัดสินใจ) |

## เทียบผลลัพธ์

| มิติ | Before | After |
|---|---|---|
| วิธีจับดราม่า | ตาคนไล่ส่อง | AI + spike detection อัตโนมัติ |
| ความครอบคลุม | เท่าที่คนเฝ้าไหว | ทุกเพจ ทุกช่วงเวลา |
| มาตรฐานการตัดสิน | อัตวิสัย | คงที่ (โมเดล + threshold เดียว) |
| รู้ตัวตอน | เริ่มลุกลาม | ตั้งแต่เริ่มพุ่ง (spike แรก) |
| หลักฐานเชิงตัวเลข | ไม่มี | severity/baseline/topic/reach จริง |

## ใครได้ประโยชน์ + เรื่องถูกส่งต่อไปทีมไหน

**Before:** ทุกเรื่องกองที่ทีม Community ทีมเดียว แล้วค่อย ๆ ไล่ถามต่อว่า "อันนี้ใครดู?"
**After:** ระบบจัดประเด็นให้แล้วว่าเป็นเรื่องของใคร → alert เด้งเข้า Discord channel ของทีมนั้นโดยตรง

| ประเด็นที่ AI จับได้ | ทีมที่รับเรื่อง | เอาไปตัดสินใจอะไร |
|---|---|---|
| บั๊ก/เทคนิค (เข้าเกมไม่ได้, เซิร์ฟล่ม, installer) | **Dev / QA** | hotfix เดี๋ยวนี้ หรือ rollback แพตช์ |
| ของรางวัล/โค้ด (โค้ดไม่ติด, ดูโฆษณาแล้วไม่ได้ของ) | **Marketing (แคมเปญ) + CS** | หยุด/ต่ออายุแคมเปญ, ตั้งรอบชดเชย, เตรียมสคริปต์ตอบ CS |
| เติมเงิน/ราคา (กาชาแพง, เงินหาย) | **Marketing / Monetization** | ปรับราคา/อัตราดรอป, ทำรอบคืนเงิน |
| สมดุล/ความเป็นธรรม (p2w, อิมบา) | **Game Design** | ปรับ balance รอบถัดไป |
| บริการ/ทีมงาน (ตอบช้า, โทษผู้เล่น) | **Community / CS** | ปรับ tone แถลง, เพิ่มกำลังคนตอบ |
| คอนเทนต์/อีเวนต์ | **Content / Event** | ปรับกติกา/ระยะเวลากิจกรรม |

| ทีม | ได้อะไรจาก Crisis Radar |
|---|---|
| **Community / Social** | เลิกไล่ส่องเอง — รู้ทันทีว่าต้องเข้าไปตอบตรงไหนก่อน (เรียงตาม reach) |
| **Dev / QA** | รู้ว่าบั๊กไหนกระทบคนจริงเยอะสุด ใช้จัดลำดับ hotfix แทนการเดา |
| **Marketing** | วัดผลแคมเปญจากเสียงจริง ไม่ใช่แค่ยอดกด + จับแคมเปญที่พังได้ในชั่วโมงแรก |
| **Game Design** | เห็น pattern คำบ่นเรื่อง balance สะสมเป็นตัวเลข ไม่ใช่ความรู้สึก |
| **หัวหน้าทีม / ผู้บริหาร** | เห็นสถานะทุกเกมในหน้าเดียว ใช้ตัดสินใจว่าต้องออกแถลงระดับบริษัทไหม |

## Metric ที่จะวัดตอน pilot 15 วัน (Impact)
- **Detection lead time**: เวลาจาก "คอมเมนต์ลบเริ่มพุ่ง" → "ทีมได้รับ alert" (เป้า: เร็วกว่าคนเฝ้าเดิม)
- **Coverage**: จำนวนเพจ/เกมที่เฝ้าได้พร้อมกัน (Before ≈ เท่าที่คนไหว → After = ทุกเพจ)
- **เวลา manual ที่ประหยัด**: ชม./วันที่ทีมไม่ต้องนั่งไล่ส่อง
- **True/False alert rate**: alert ที่เป็นวิกฤตจริง เทียบ false alarm (ปรับ threshold ต่อเนื่อง)
